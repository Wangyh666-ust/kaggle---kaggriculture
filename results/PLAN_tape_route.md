# 决策：v21 起改用「磁带路线」（2026-09-21）

## 背景（实证）

解码核实了 10 个公开高分实现（`results/top_notebooks_findings.md` 第 H 节）：
**10/10 都是 720 步动作磁带**，没有一个是规则引擎。它们之间只有两个半磁带族：

- **族 A**：thomastschinkel 的 `Chassis` + yhay81 的 shop-router 磁带
  （`{actions: 3982, routes: 41×719, shops: 64}`）—— 7 个实现共用，
  其中 prvsiyan / reyhanksatria / guruprasaathas111 内嵌的 blob 逐字节相同
- **族 B**：单条 `_ACTIONS` 720 步表 + 反射层（boatlee / salem2900）
- tetsutani 是第三种变体（5 条按店铺选路的自建磁带）

它们之间的差距**不在策略搜索**，而在三件执行层面的事：选哪条磁带、
卖单时机微调（sell_lead / RACE / ORDERPRI）、执行修补（杂草/仓库/手数）。

## 我方现状与判断

规则式 agent 迭代到 v15 后，6 个改进变体（v16-v20）全部未能超越 v15
（见 `results/top_notebooks_findings.md` 第 F、G 节）。诊断结论：
**农场执行效率打不过手工优化的磁带**——对手 1 个工人管 ~8 棵作物，
我们只有 4-5 棵；他们种 40-78 棵，我们种 15-36 棵。规则式在当前架构
（全局贪心派活）下已到局部最优。

## 决策

**v21 起改用磁带底盘**，具体：

1. **底盘**：采用 thomastschinkel 的 `Kaggriculture v9/3`（farm2945 notebook
   内可见的完整 5759 行提交文件，实测 Elo 2944.7）。理由：代码完全公开可见
   （不是混淆 blob）、自包含（仅标准库）、且是该族最新的完整实现。
2. **归属与许可**：文件头部保留了 Apache-2.0 归属声明与上游许可证
   （thomastschinkel / yhay81 / tetsutani / prvsiyan / Dmitrii Gluzdov 等）。
   我们在此基础上继续开发，保留全部 NOTICE。
3. **我们的增量**：把规则式时代打磨出的市场层作为**附加层**移植上去，
   逐个验证（每个改动都要过 smoke + 双座位头对头）：
   - 卖单槽位按对手可售暴露度排序（我们验证过的思路，2945 也有 ORDERPRI2）
   - base-price 闸门（只在报价高于基准价时抢跑）
   - 对手销量还原（Δinventory + 城镇消耗 − 自己销量）
   - 我们的甜瓜/草莓/畜群的**数量规则**不移植（磁带已定死布局，改了会脱轨）
4. **评测纪律**（沿用并加强）：
   - 任何改动先跑 `scripts/smoke.py`（9 种子 × 双座位，断言 DONE 且资金 > $10k）
   - 头对头用同种子集、双座位、≥20 局，报 mean + worst 资金差
   - 只打平或变差的改动一律回退并记录到 findings（v16-v20 已示范）

## 版本管理

- `master`：规则式路线（v15 为终点，冻结，标签 `submit-v15`）
- `tape-route` 分支：磁带路线开发（v21 起）
- 每次提交 Kaggle 打标签 `submit-vXX`，注明线上分数
- 提交文件约定：**分支根目录的 `main.py` 即当前提交文件**；
  规则式版本在分支里改名为 `legacy/main_rule_v15.py`，避免混淆

## 风险

1. **同质化**：族 A/B 被大量选手共用，镜像对局接近零和；真正的增量必须来自
   我们自己的层（市场层）或选带策略（对手开局签名匹配）。
2. **脆弱性**：磁带遇到布局扰动会失准（杂草挡位、对手动作差异）——
   我们的规则式经验在这里反而是资产，可作为修补层的思路来源。
3. **许可**：所有公开 notebook 均为 Apache-2.0 派生，保留归属即可；
   不改变"这是基于公开工作的二次开发"这一事实，需在 README 写明。
